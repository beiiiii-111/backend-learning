# 单元 11 课后练习

> 模块五 · 综合项目实战 › 单元 11

这个单元的练习全部围绕综合项目，**做完之后的产物可以直接进项目仓库**。

练习分两部分：

- **必做**

  ：跟上课程进度走的四道题，做完能保底跑通活动管理模块。
- **选做**

  ：想拿高分的同学做，覆盖更细的边界情况。

每道题下面有验收标准表。**自己先跑一遍验收标准，再交。** 老师检查时就是按这张表逐项验的。

## 必做 1：补全页面清单与接口清单

### 要求

为“场次与场地”和“报名审核”两个模块，各写一份清单文档，包含四张表：

1. **实体表**

  —— 有哪些实体、每个实体有哪些关键字段
2. **动作表**

  —— 谁能对实体做什么、做完状态怎么变
3. **页面清单**

  —— 页面、路由、主要接口、可访问角色
4. **路由表**

  —— 直接可以贴进routes.js的代码

保存为 `docs/design/module-session.md` 和 `docs/design/module-signup.md`（放在你自己的项目仓库里，不是教程站点里）。

### 验收标准

| 检查项 | 通过标准 |
| --- | --- |
| 实体判断有依据 | 每个实体的判断理由能说出来（有自己的 id、会被单独查询） |
| 流程和标记分开了 | 状态字段是单向流程，下架 / 启用这类是独立标记 |
| 页面职责不重叠 | 不存在两个页面做同一件事 |
| 新增和编辑共用组件 | 路由表里两条路由指向同一个组件文件 |
| 静态路由在动态路由前面 | `create` 写在 `:id` 前面 |
| 清单能互相反推 | 页面清单的每个接口都在接口清单里，接口清单没有孤儿接口 |
| 标出了需要跨表判断的动作 | “占用场地”这类要查别的数据才能判断的动作有标注 |

## 必做 2：搭出完整的工程骨架

### 要求

建一个 Vite + Vue 3 工程，达到下面的状态：

- 目录结构符合11.2的规划
- 路由表覆盖至少“登录 + 活动管理 + 报名审核 + 场次与场地 + 数据看板”五个入口
- 后台布局能跑起来：侧边栏、顶栏、面包屑、内容区
- 菜单能点、能高亮（包括详情页和编辑页）
- 未登录访问后台页面会被跳到登录页
- 浏览器标签页标题跟着页面变

### 验收标准

| 检查项 | 怎么验证 |
| --- | --- |
| 登录页没有侧边栏 | 访问 `/login`，看不到菜单 |
| 后台页面有侧边栏 | 访问 `/dashboard`，左侧菜单、顶部面包屑都在 |
| 菜单能跳转 | 点每个菜单项，地址栏和内容区都跟着变 |
| 详情 / 编辑页菜单仍高亮 | 直接访问 `/activity/create`，侧边栏“活动管理”是高亮的 |
| 面包屑跟着变 | 从列表进编辑页，面包屑变成“活动管理 / 编辑活动” |
| 未登录会被拦 | 清掉本地 token，访问 `/activity`，跳回 `/login` 且带 `?redirect=` |
| 只有内容区滚动 | 把一个页面内容撑长，侧边栏和顶栏固定不动 |
| 宽表格不撑破布局 | 表格列数多时，横向滚动条出现在内容区内部 |
| 标签页标题跟着变 | 切页面，看标签文字 |
| 目录结构符合规划 | `views/` 按业务模块分，`api/` 按模块分文件 |
| 没有三级以上的相对路径 | 全局搜 `../../`，应为 0 结果 |
| 没有提交 `node_modules` | `git ls-files \| grep node_modules` 应为空 |

## 必做 3：完成活动列表页

### 要求

按 [11.4](04-11.4-列表页标准做法.md) 的模板做 `ActivityList.vue`，包含：

- 查询条件：关键字、状态（两个都要能用）
- 表格：标题、类型、状态、报名情况、报名截止、操作
- 行操作：详情、编辑、下架 / 恢复、删除
- 分页：页码、每页条数
- 四态齐全
- 删除有二次确认，成功后自动刷新

数据可以先用 mock（本地假数据或 `json-server`），接口层按[接口约定](../../06-综合项目/04-接口约定.md)的真实路径写。

### 验收标准

| 检查项 | 怎么验证 |
| --- | --- |
| 查询能生效 | 输入关键字点查询，看请求参数里有没有 `keyword` |
| 查询后回到第 1 页 | 翻到第 3 页，改状态筛选，点查询，看请求参数里 `page` 是不是 1 |
| 每页条数能改 | 改成 20，回到第 1 页，列表显示 20 条 |
| 重置能恢复初始条件 | 点重置，条件清空且列表刷新 |
| 加载中有反馈 | 网络面板限速，看有没有 loading 遮罩 |
| 无数据状态有引导 | 查一个不存在的关键字，看提示和“立即创建”按钮 |
| 失败状态有重试 | 把接口地址改错，看错误信息和“重新加载”按钮 |
| 删除有二次确认 | 点删除，看有没有确认弹窗 |
| 取消删除不请求接口 | 点取消，看网络面板有没有发请求 |
| 删除后自动往前翻页 | 翻到最后一页并删光该页数据，看是否自动回到上一页 |
| 下架后状态立刻变 | 点下架，确认后看表格里的标签是否变成“已下架” |
| 操作列按钮跟状态对上 | 造一条“已结束”的活动，看“编辑”按钮是否消失 |
| 表格有 row-key | 检查代码里的 `row-key="id"` |

## 必做 4：完成活动表单页

### 要求

做 `ActivityForm.vue`，新增和编辑共用，包含：

- 字段：标题、类型、名额、报名截止时间、活动说明
- 校验：必填、长度、名额为正整数、截止时间晚于当前时间
- 编辑模式下：名额不能小于已通过人数、截止时间只能往后退
- 提交：submitting状态、防重复提交、成功提示、失败不跳转
- 未保存离开提醒

### 验收标准

| 检查项 | 怎么验证 |
| --- | --- |
| 新增和编辑是同一个文件 | `views/activity/` 下只有一个 `ActivityForm.vue` |
| 新增模式字段为空 | 访问 `/activity/create`，所有字段是空的 |
| 编辑模式字段有值 | 从列表点编辑，字段都回填了 |
| 必填校验能触发 | 什么都不填点提交，看有没有红字 |
| 标题长度校验 | 输入 1 个字符，看是否提示 |
| 名额整数校验 | 输入 2.5，看是否被拦 |
| 截止时间校验 | 选一个过去的时间（手动输入绕过置灰），看是否报错 |
| 提交按钮有 loading | 点提交，看按钮是否变 loading |
| 连点两次只创建一条 | 快速点两次提交，看列表里是不是只有一条 |
| 校验失败不请求接口 | 填错一个字段后提交，看网络面板有没有发请求 |
| 提交失败按钮恢复 | 把接口地址改错，提交失败后按钮能再点 |
| 提交成功有提示并跳转 | 看是否提示并回到列表 |
| 提交成功后列表有新数据 | 回列表，看有没有刚创建的活动 |
| 编辑时名额下限生效 | 造一条已有 5 人通过的活动，把名额改成 3，看是否报错 |
| 离开未保存表单有提醒 | 填一个字段，点侧边栏菜单，看有没有确认弹窗 |
| 提交成功跳转不弹提醒 | 提交成功时不应弹“未保存”提示 |

## 选做 1：把列表和表单抽成可复用的“页面模板”

### 要求

把列表页的标准做法抽成三个通用件：

- useTable（11.4已经给了，可以再改进）
- StateWrapper.vue：统一处理加载中与失败状态
- useFormPage.js：统一处理新增 / 编辑共用的表单逻辑

然后用这套通用件**重写一遍**活动列表页和表单页，对比重写前后的代码量。

### 验收标准

| 检查项 | 通过标准 |
| --- | --- |
| 三个通用件都有 | 文件存在且能独立说明职责 |
| 重写后代码量减少 | 给出前后行数对比（用 `wc -l`） |
| 通用件有默认行为 | 不传可选配置也能跑 |
| 通用件没有写死业务 | 里不出现 `activity`、`Activity` 这类业务词 |
| 有说明文档 | 写清每个通用件的参数和适用场景 |

## 选做 2：给列表页加上批量操作

### 要求

活动列表支持多选，选中后可以：

- 批量下架
- 批量删除（只有全为草稿时才允许）
- 跨页保留勾选

### 验收标准

| 检查项 | 怎么验证 |
| --- | --- |
| 能多选 | 勾选几行，看底部/顶部有没有显示选中数量 |
| 批量下架生效 | 勾 3 条，点批量下架，看 3 条状态都变了 |
| 批量删除有条件限制 | 选中包含“报名中”的活动时，批量删除按钮应禁用并说明原因 |
| 跨页保留勾选 | 第 1 页勾 2 条，翻到第 2 页，之前勾的还在 |
| 翻页后能正确清空 | 提供一个“清空选择”的入口 |
| 全选只选当前页 | 点表头全选，只勾选当前页（不要跨页全选） |

## 选做 3：给项目写一份设计文档

### 要求

在项目仓库里写 `docs/design/DESIGN.md`，包含：

1. 项目背景与目标用户
2. 页面清单与路由表（必做 1 的成果）
3. 数据模型（实体、字段、关系）
4. 状态机说明（用文字或图）
5. 目录结构说明
6. 关键设计决策（每条写清“选了什么 / 为什么 / 代价是什么”）
7. 已知限制与后续计划

### 验收标准

| 检查项 | 通过标准 |
| --- | --- |
| 设计决策有取舍说明 | 每条决策都写了“代价是什么” |
| 状态机表述无歧义 | 能据此写出 `canSignup(activity)` 这个函数 |
| 数据模型有字段类型 | 不是只写字段名 |
| 已知限制诚实 | 至少 3 条，且是真的限制 |
| 没有空话 | 不出现“提升用户体验”“架构清晰”这类无法验证的说法 |

## 选做 4：挑出一个真实存在的坑并写清楚

### 要求

在你自己写代码的过程中，至少会遇到一个“现象 - 原因 - 处理”完整的坑。把它写清楚，要求：

- 现象可以被复现（写清复现步骤）
- 原因分析到源码或规范层面，不停留在“反正就是这样”
- 处理方式给出代码
- 说明同类问题以后怎么避免

### 验收标准

| 检查项 | 通过标准 |
| --- | --- |
| 现象可复现 | 步骤写清楚，别人照着能复现 |
| 原因有依据 | 引用了官方文档，或给出了自己的验证过程 |
| 处理方式给代码 | 不是“注意一下就好” |
| 有预防措施 | 写清下次怎么不踩 |
