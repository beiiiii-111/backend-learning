## 一、整体思路

本次作业的核心不是"再写一遍 CRUD"，而是把笔记第 2 节的概念落到代码里，验证它们**真的生效**：

1. **条件构造器**：用 `LambdaUpdateWrapper` 按非主键字段更新（对比 `updateById` 只能按主键）
2. **序列化格式**：用 `@JsonFormat` 控制时间字段的输入输出格式
3. **类型映射**：新建表时按笔记 2.5 的表选 MySQL 类型，并对应正确的 Java 类型
4. **批量操作**：`saveBatch` / `removeByIds`，观察批量 SQL 的刷写
5. **连接池**：主动把池调小制造故障，看报错长什么样、怎么解释
6. **事务**：两个写操作放一个事务里，用"故意失败"验证原子性
7. **逻辑删除 + 自动填充**：在新表上复用全局配置，验证 UPDATE 而不是 DELETE

验证方式统一为：**接口调一次 → 看响应 → 再直接查库确认**。只信接口返回不够，比如逻辑删除后接口查不到，必须查库确认 `deleted=1`、行还在。

## 二、逐题做法

### 基础 1 · 给 t_user 加 email 字段，用 LambdaUpdateWrapper 按 username 更新邮箱

**做法**

`t_user` 原本就有 `email VARCHAR(100)`（笔记 3.1 的建表脚本里已经包含），所以不需要 `ALTER`，直接在 Service 里补更新方法：

```java
// UserService
boolean modifyEmailByUsername(String username, String email);

// UserServiceImpl
@Override
public boolean modifyEmailByUsername(String username, String email) {
    if (!StringUtils.hasText(username)) {
        throw new IllegalArgumentException("username 不能为空");
    }
    if (!StringUtils.hasText(email)) {
        throw new IllegalArgumentException("email 不能为空");
    }
    return update(new LambdaUpdateWrapper<User>()
            .eq(User::getUsername, username)
            .set(User::getEmail, email)
            // 踩坑：update(wrapper) 不带实体时，MetaObjectHandler 的 updateFill 不会触发，
            // update_time 不会刷新，只能显式 set
            .set(User::getUpdateTime, LocalDateTime.now()));
}
```

Controller：`PUT /users/email?username=zhangsan&email=zhangsan_new@example.com`

**为什么用 LambdaUpdateWrapper 而不是 updateById**

- `updateById` 只能按**主键**更新，而且要把实体整个传进来，通常得先 `getById` 查一次；
- `update(Wrapper)` 直接把条件写进 `WHERE`，一条 SQL 搞定，条件是**方法引用**（`User::getUsername`），改字段名时编译器报错，手写 `"username"` 字符串不会。

**实测结果**

```
更新前: GET /users/2  → email = zhangsan@example.com
PUT /users/email?username=zhangsan&email=zhangsan_new@example.com → true
更新后: GET /users/2  → email = zhangsan_new@example.com, updateTime 已刷新
```

生成的 SQL：`UPDATE t_user SET email=?, update_time=? WHERE username=? AND deleted=0`
（`AND deleted=0` 是全局逻辑删除自动追加的）

### 基础 2 · 给 score 之外的字段补上 @JsonFormat

**做法**

给所有**时间类型**字段加 `@JsonFormat`：

| 字段 | MySQL | 注解 |
| --- | --- | --- |
| `birthday` | `DATE` | `@JsonFormat(pattern = "yyyy-MM-dd")` |
| `workTime` | `TIME` | `@JsonFormat(pattern = "HH:mm:ss")` |
| `lastLoginTime` | `DATETIME` | `@JsonFormat(pattern = "yyyy-MM-dd HH:mm:ss")` |
| `createTime` | `DATETIME` | 同上 |
| `updateTime` | `DATETIME` | 同上 |

**为什么 score 不加**

`@JsonFormat` 的 `pattern` 只对日期/时间类型有意义。`score` 是 `FLOAT`（近似小数，存的是评分不是金额），Jackson 对数值类型不支持日期 pattern，加了也没效果（还可能报错）。金额类字段要精确应该用 `DECIMAL` + `BigDecimal`，那也不是格式化能解决的问题。

**实测结果（输出）**

```json
"birthday": "1995-01-15",
"workTime": "09:00:00",
"lastLoginTime": "2026-10-01 09:00:00",
"createTime": "2026-10-01 09:00:00",
"updateTime": "2026-10-01 09:00:00",
"score": 4.8
```

**实测结果（输入）**：`POST /users` 传 SQL 风格字符串能正常接收

```json
{"username":"zhouba","age":28,"birthday":"1997-05-20",
 "workTime":"09:00:00","lastLoginTime":"2026-10-10 20:00:00"}
```
→ 返回 `id=6`，各时间字段正常解析落库。不加注解的话 Jackson 只认带 `T` 的 ISO 格式（`1997-05-20T00:00:00`）。

### 进阶 1 · 新增 t_course（id / name / teacher / credit），练 saveBatch 与 removeByIds

  ```java
      return saveBatch(courses);   // 默认每 1000 条 flush 一次

  public boolean removeCourseBatch(List<Long> ids) {
      return removeByIds(ids);     // 真正的 DELETE ... WHERE id IN (...)
  }
  ```
- `controller/CourseController.java`：`POST /courses`、`POST /courses/batch`、`GET /courses`、`GET /courses/{id}`、`DELETE /courses/batch?ids=4,5`

**实测结果**

### 进阶 2 · 池调成 1 复现 Connection is not available，再调回默认值对照 Druid 监控页

**思路**

要在连接池上看出问题，必须让请求**真的攥着连接不放**——普通查询几毫秒就还了，压不出来。所以写一个"事务内先查库再 sleep"的方法：

```java
@Transactional(rollbackFor = Exception.class)
@Override
public void slowQuery(long holdMillis) {
    list();                       // 首次访问数据库，从池里取走连接
    try {
        Thread.sleep(holdMillis); // 事务没结束，连接不归还
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
    }
}
```

接口：`GET /users/slow?ms=5000`

**关键前提**：`@Transactional` 方法执行到第一条 SQL 时从池里借连接，**方法结束（提交/回滚）才归还**。所以 sleep 期间连接是被占住的。

**复现步骤**

1. 改 `application.yml`：`maximum-pool-size: 1`、`minimum-idle: 1`，重启
2. 并发 5 个请求：`bash scripts/pool-demo.sh 5 5000`
3. 观察结果，再改回 `10` / `5` 重启，用同一脚本跑一遍对照

**实测结果（池 = 1，并发 5）**

```
请求 1: HTTP 200, 耗时约 6s, 响应 = done after 5000ms
请求 2: HTTP 500, 耗时约 4s, 响应 = {"message":"Could not open JDBC Connection for transaction","status":500}
请求 3: HTTP 500, 耗时约 5s, ...
请求 4: HTTP 500, 耗时约 5s, ...
请求 5: HTTP 500, 耗时约 5s, ...
```

**实测结果（池 = 10，并发 5，对照）**

```
请求 1~5: 全部 HTTP 200，耗时约 7~8s
```

**怎么解释这两个现象**

- 只有 1 个连接：请求 1 借走后睡 5 秒，其余 4 个在池外排队，等满 3 秒（`connection-timeout`）就放弃，抛
  `SQLTransientConnectionException: backend-learning-pool - Connection is not available, request timed out after 3000ms`，
  被全局异常处理器包成了上面的 500 响应。**失败请求耗时 ≈ 3 秒（超时时间），而不是 5 秒（占用时间）**，这一点很关键。
- 池 = 10：5 个并发各借一条，都能拿到，全部成功，且总耗时只比单次多一点点——说明池够用时并发不会排队。

**Druid 监控页对照**

Druid 依赖放在 Maven profile 里（默认构建仍是 HikariCP，避免 Druid 自动配置顶掉 Hikari）：

```bash
mvn -pl 05-mybatis -Pdruid spring-boot:run \
  -Dspring-boot.run.arguments="--spring.profiles.active=druid --spring.datasource.druid.max-active=1"
```

监控页 `http://localhost:8005/druid/`，账号 `admin` / `admin`。

压测进行中登录监控页，Datasource 页显示：

```
MaxActive  = 1     池上限
ActiveCount = 1    活跃连接，已经满了
PoolingCount = 0   空闲连接，没了
NotEmptyWaitCount = 12   有多少次取连接时池是空的（排队次数）
ExecuteCount = 20
```

### 挑战 · 新增 t_order，演示「创建订单 + 扣库存」的事务原子性，并加逻辑删除与自动填充

**表设计**

| 表 | 字段 | 类型 | 说明 |
| --- | --- | --- | --- |
| `t_product` | `id` | `BIGINT UNSIGNED` | 主键 |
| | `name` | `VARCHAR(100) NOT NULL` | 商品名 |
| | `price` | `DECIMAL(12,2) NOT NULL` | **金额用定点数** |
| | `stock` | `INT NOT NULL DEFAULT 0` | 库存 |
| | `create_time` / `update_time` | `DATETIME NOT NULL` | 自动填充 |
| `t_order` | `id` | `BIGINT UNSIGNED` | 主键 |
| | `order_no` | `VARCHAR(32) NOT NULL`，唯一索引 | 订单号（定长业务编号，这里用 `VARCHAR` 便于以后加前缀） |
| | `user_id` / `product_id` | `BIGINT UNSIGNED NOT NULL` | 关联 id，与 `t_user.id` 类型保持一致 |
| | `quantity` | `INT NOT NULL DEFAULT 1` | 数量 |
| | `amount` | `DECIMAL(12,2) NOT NULL` | 金额 = 单价 × 数量 |
| | `status` | `TINYINT NOT NULL DEFAULT 0` | 0 待支付 / 1 已支付 / 2 已取消 |
| | `create_time` / `update_time` | `DATETIME NOT NULL` | 自动填充 |
| | `deleted` | `TINYINT NOT NULL DEFAULT 0` | 逻辑删除（全局配置已生效） |

**核心代码**

```java
@Transactional(rollbackFor = Exception.class)
@Override
public Order createOrder(Long userId, Long productId, Integer quantity) {
    // ...参数校验...
    Product product = productMapper.selectById(productId);

    Order order = new Order();
    order.setOrderNo(generateOrderNo());
    // ...
    // 第一步：先写库（createTime / deleted 由 MetaObjectHandler 自动填充）
    save(order);

    // 第二步：校验库存，不够就抛异常，观察第一步的 insert 是否被回滚
    if (product.getStock() < quantity) {
        throw new RuntimeException("库存不足：剩余 " + product.getStock() + "，需要 " + quantity + "，事务回滚");
    }

    // 第三步：扣库存
    product.setStock(product.getStock() - quantity);
    productMapper.updateById(product);
    return order;
}
```

**为什么故意"先写库再校验"**

和笔记步骤 9 里 `createUser` 的写法保持一致：如果把库存校验放在 insert 之前，那订单还没写进去就抛异常了，**看不出回滚发生过**。先 insert 再抛异常，才能证明"已执行的写操作被撤销"——这才是要演示的原子性。

**自动填充与逻辑删除怎么生效的**

这两项都是**全局配置**，新表不用重复配：

```yaml
mybatis-plus:
  global-config:
    db-config:
      logic-delete-field: deleted     # 有 deleted 字段的实体自动逻辑删除
      logic-delete-value: 1
      logic-not-delete-value: 0
```

`MyMetaObjectHandler` 按**字段名**填充，`t_order` 的 `createTime` / `updateTime` / `deleted` 名字对得上，自动就生效了（Order 没有 `version` 字段，`strictInsertFill` 会跳过，不会报错）。

**实测结果**

```
① 下单前库存：stock = 10
② POST /orders?userId=1&productId=1&quantity=2
   → ORD20261010223517476, qty=2, amount=199.0, status=0,
     createTime=2026-10-10 22:35:17（自动填充）, deleted=0
③ 下单后库存：stock = 8          ← 订单 + 扣库存都成功
④ POST /orders?...&quantity=999 → HTTP 500 "库存不足：剩余 8，需要 999，事务回滚"
⑤ 回滚后：订单条数仍为 1，库存仍为 8   ← 订单 insert 被撤销，库存没动
⑥ DELETE /orders/1 → true
   GET /orders/1 → 空（逻辑删除过滤）
   查库：deleted = 1，update_time = 22:35:34 已刷新，物理行还在
```

## 三、本次踩到的两个坑

1. **`update(Wrapper)` 不带实体时，`MetaObjectHandler.updateFill` 不触发**
   表现：邮箱更新成功了，但 `update_time` 还是旧值。
   原因：自动填充作用在实体对象上，`update(wrapper)` 是"无实体更新"，没有可填充的载体。
   解决：在 wrapper 里显式 `.set(User::getUpdateTime, LocalDateTime.now())`。

2. **连接池实验压不出来**
   表现：并发打普通查询接口，QPS 再高也不报错。
   原因：普通查询执行完立刻归还连接，占用时间是毫秒级，池根本不会满。
   解决：必须在**事务内**执行 SQL 后再 sleep，让连接在整个 sleep 期间被占用，才能制造排队。

   > "注意失败请求耗时是 3 到 5 秒，也就是 `connection-timeout` 3000 毫秒，不是 5 秒。
   > 这说明它们是在'等连接'超时，不是'执行慢'。底层异常是
   > `SQLTransientConnectionException: Connection is not available, request timed out after 3000ms`。"
5. 把 `maximum-pool-size` 改回 `10`，重启，再跑一次脚本：
   > "5 个全部 200，总耗时只比单次多一点，说明池够用时并发不排队。"
6. 切到 Druid 演示（可选，需提前用 `-Pdruid` 启动）：
   - 浏览器打开 `http://localhost:8005/druid/`，admin/admin 登录
   - 压测中刷新 Datasource 页，指出 `ActiveCount = 1`、`PoolingCount = 0`、`NotEmptyWaitCount` 在涨
   - 对照 `max-active=10` 时的数字

### 5. 挑战：订单事务原子性（约 2 分 30 秒）

1. 打开 `schema.sql` 的 `t_order` / `t_product`，讲 `amount` 用 `DECIMAL(12,2)`
2. 打开 `OrderServiceImpl.createOrder`，讲三步顺序：
   > "故意先 insert 再校验库存。如果先校验，订单还没写进去就抛异常了，看不出回滚发生。
   > 先写再抛，才能证明'已经执行的写操作被撤销'。"
3. 终端演示成功路径：
   ```bash
   curl -s http://localhost:8005/products/1          # stock = 10
   curl -s -X POST "http://localhost:8005/orders?userId=1&productId=1&quantity=2"
   curl -s http://localhost:8005/products/1          # stock = 8
   ```
4. 演示失败路径：
   ```bash
   curl -s -X POST "http://localhost:8005/orders?userId=1&productId=1&quantity=999"
   curl -s http://localhost:8005/orders     # 条数还是 1
   curl -s http://localhost:8005/products/1 # stock 还是 8
   ```
   > "订单没多出来，库存也没少，两个写操作是原子的。"
5. 演示逻辑删除 + 自动填充：
   ```bash
   curl -s -X DELETE http://localhost:8005/orders/1   # true
   curl -s http://localhost:8005/orders/1             # 空
   mysql -uroot -p123456 -D backend_learning -e "SELECT id, deleted, update_time FROM t_order;"
   ```
   > "接口查不到，但库里这行还在，deleted = 1，update_time 也刷新了。"

### 6. 收尾（约 30 秒）

> "总结一下：条件构造器用方法引用更安全；时间字段要靠 @JsonFormat 定格式；
> 建表按数据形态选类型、金额用 DECIMAL；批量操作记得配事务；
> 连接池要按 CPU 核数和 MySQL max_connections 一起算上限；
> 事务要保证多个写操作的原子性，注意自调用失效的问题。
> 另外这次踩了两个坑，一个是 update(Wrapper) 不会触发自动填充，一个是连接池实验需要事务内 sleep 才压得出来。"
